# 将签到批次设计为可持久化的服务端执行对象

当前批量签到主要在请求生命周期内完成，页面刷新或离开后无法可靠恢复进度；工作台还部署在 Cloudflare 代理域名后，长时间占用浏览器到源站的 HTTP 请求存在超时风险。决定将签到批次作为由服务端持久化并后台执行的业务对象，批次创建请求只负责校验、锁定范围和入队后立即返回，工作台通过禁止缓存的短请求轮询进度；现有同步批量调用保持兼容，异步模式作为增量能力提供给工作台。这样可以在不引入 WebSocket、且适应 Cloudflare 代理和 1C1G 服务器约束的前提下，保证签到范围、执行状态和结果可追踪。

## 考虑过的方案

- 保持同步执行：实现简单，但无法满足刷新后恢复和持续进度展示。
- 使用 SSE 或 WebSocket：实时性更强，但会增加连接管理和低配部署复杂度。
- 持久化批次并轮询：增加批次生命周期管理，但实现边界清晰、兼容性和部署成本更可控，因此采用此方案。
- 让 Cloudflare 代理请求等待外部站点完成：受代理超时影响，且断线时无法可靠判断是否已创建或执行，因此不采用。

## 结果

- 批次离开页面后继续执行，第一阶段不提供服务端中途取消。
- 批次汇总与逐账号签到记录同时保留，并遵循同一清理策略。
- 前端必须能够处理执行中、已完成、部分失败和全部失败等批次状态。
- 批量确认时锁定签到范围，后续列表变化不影响已创建批次。
- 创建请求使用幂等标识，网络重试不会重复创建批次；工作台断线后凭 `batchId` 恢复轮询。
- 单账号外部请求沿用有限超时；单个账号超时记为可重试失败，批次继续执行后续账号。
- 状态查询返回 `Cache-Control: no-store`，避免 Cloudflare 返回过期批次进度。
- 服务端重启后的批次恢复不属于本 ADR 的第一阶段范围。
