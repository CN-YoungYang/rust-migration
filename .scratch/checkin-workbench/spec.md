# 签到工作台完善

## Problem Statement

当前平台已经具备签到账号管理、单账号签到、批量签到、签到记录、余额刷新和自动调度等能力，但管理员缺少一个围绕“今日签到运营”的统一工作台。

现有前端批量签到主要循环调用单账号签到接口，而后端已经存在另一套批量签到语义，导致批次触发类型、每日尝试上限、跳过规则和结果展示不完全一致。当前批量进度主要保存在页面内存中，刷新或离开页面后无法可靠恢复；账号列表也不能清晰表达完整的可执行范围、批次状态和失败处理路径。系统通过 Cloudflare 代理域名访问时，任何等待整批外部签到完成的 HTTP 请求还存在代理超时和断线重试造成重复执行的风险。

## Solution

新增“签到工作台”作为登录后的默认页面，围绕管理员完成今日签到运营的完整闭环：查看状态概览、筛选签到账号、预览并确认签到范围、创建签到批次、查看服务端执行进度、查看批次汇总和逐账号结果，以及重试失败账号。

## Implementation Status

本规格对应的代码实现和自动化验证已完成。当前仅保留真实 Cloudflare 挂载域名环境的浏览器人工验收，重点确认代理超时、短暂断线后的批次恢复、移动端抽屉布局和实际部署配置；该验收不改变已确定的业务边界，也不要求在本地模拟外部部署环境。

签到批次由服务端持久化并在后台执行。工作台使用快速返回的异步批次创建模式并通过禁止缓存的短请求轮询状态；现有同步批量调用保持兼容，但工作台不使用会等待外部签到完成的同步模式。批次确认时锁定签到范围，页面刷新、离开或 Cloudflare/浏览器短暂断线不影响执行，前端通过 `batchId` 恢复查看。单个站点请求超时只影响对应账号，批次继续处理后续账号。工作台与现有账号管理、签到记录、统计、通知和全局设置页面保持清晰分工。

## User Stories

1. 作为管理员，我希望登录后直接看到签到工作台，以便立即了解今日签到运营情况。
2. 作为管理员，我希望看到今日成功数、失败数、待处理数和余额预警数，以便快速判断是否需要介入。
3. 作为管理员，我希望查看执行中的签到批次和最近批次，以便知道当前工作是否仍在进行以及上次结果如何。
4. 作为管理员，我希望看到最近失败的签到账号，以便优先处理可重试问题。
5. 作为管理员，我希望按关键词、站点、所属用户、账号状态、今日签到结果和余额预警筛选签到账号，以便缩小运营范围。
6. 作为管理员，我希望系统默认识别当前筛选范围内的可执行账号，以便快速准备今日签到。
7. 作为管理员，我希望在确认前取消部分账号，以便不必重新调整整个筛选条件。
8. 作为管理员，我希望在确认前看到账号总数、预计执行范围、已签到账号、停用账号、达到每日上限账号及各自跳过原因，以便避免误操作。
9. 作为管理员，我希望确认后创建一个签到批次，以便把本次操作作为一个可追踪的整体管理。
10. 作为管理员，我希望批次创建后立即看到执行中状态，以便不必等待所有账号完成才知道操作是否已经开始。
11. 作为管理员，我希望看到批次的总数、完成数、成功数、失败数和跳过数，以便掌握整体进展。
12. 作为管理员，我希望看到每个账号的进行中、成功、今日已签到、失败或跳过状态，以便定位具体问题。
13. 作为管理员，我希望页面刷新或离开后重新进入工作台仍能看到执行中的批次，以便不会丢失正在进行的运营任务。
14. 作为管理员，我希望同一签到账号不能同时进入多个执行中的批次，以便避免重复请求外部站点。
15. 作为管理员，我希望站点暂时不可用时看到“可重试失败”及易懂的原因，以便稍后再次处理，而不是面对无限自动重试。
16. 作为管理员，我希望对单个失败账号执行重试，以便快速处理个别异常。
17. 作为管理员，我希望批量重试失败账号，以便一次处理同一批次中的多个可重试失败。
18. 作为管理员，我希望重试产生新的签到记录而不覆盖原始失败记录，以便保留完整的运营历史。
19. 作为管理员，我希望“今日已签到”与“本次成功”分开显示，以便知道账号是此前已完成还是本次刚刚成功。
20. 作为管理员，我希望错误摘要可读、详情可复制且敏感信息已脱敏，以便排查问题而不会泄露凭据或内部细节。
21. 作为管理员，我希望直接在账号列表行执行单账号签到、刷新余额、编辑和查看记录，以便减少页面切换。
22. 作为管理员，我希望影响性操作有确认反馈，批量操作有明确的进行中和完成反馈，以便避免误操作。
23. 作为管理员，我希望账号数量超过当前单页上限时可以分页或加载更多，并看到总数量，以便不会误以为看到了全部账号。
24. 作为管理员，我希望首次使用、没有账号、没有匹配结果、加载失败和权限不足时看到明确的说明和下一步入口，以便知道如何继续。
25. 作为普通用户，我希望只看到和操作自己拥有的签到账号及相关签到信息，以便保证数据隔离。
26. 作为普通用户，我希望使用与管理员一致的核心签到工作台流程，但不接触跨用户数据和管理员配置，以便完成自己的签到运营。
27. 作为管理员，我希望在工作台看到自动调度是否启用、下一次执行时间和最近一次结果，以便确认自动签到是否正常运行。
28. 作为管理员，我希望自动调度的详细编辑仍在全局设置页面完成，以便工作台保持聚焦。
29. 作为桌面端用户，我希望使用信息密度适中、可排序和可批量选择的数据表格，以便高效处理大量账号。
30. 作为移动端用户，我希望账号列表切换为易读的卡片，并保留固定的批量操作入口，以便在窄屏上完成核心操作。
31. 作为键盘用户，我希望按钮、筛选器、表格操作和批次详情都具有清晰的焦点状态，以便不依赖鼠标完成工作。
32. 作为有动效敏感的用户，我希望系统遵循减少动效偏好，并且加载、成功和失败状态不会依赖动画才能理解。
33. 作为管理员，我希望批次汇总和关联签到记录遵循同一清理策略，以便历史数据不会无限增长并保持结果口径一致。

## Implementation Decisions

- 领域模型以“签到工作台、签到批次、签到范围、签到记录、重试记录、账号状态、余额预警、业务日期和批次汇总”为核心词汇，使用项目术语表中的定义。
- 签到批次作为持久化业务对象，至少记录批次状态、触发来源、锁定的签到范围、批次汇总、创建时间、完成时间和逐账号执行结果关联。
- 批次状态使用“执行中、已完成、部分失败、全部失败”。单个账号结果继续使用成功、今日已签到、失败和跳过等状态；两种状态不能混用。
- 批量签到由后端批次能力统一执行。单账号签到接口继续保留；现有同步批量调用保持默认兼容行为，工作台使用增量提供的异步批次模式，并通过批次状态查询获得进度。
- 批量签到由后端批次能力统一执行。单账号签到接口继续保留；现有同步批量调用保持默认兼容行为，工作台使用增量提供的异步批次模式，并通过批次状态查询获得进度。工作台不通过 Cloudflare 长时间等待同步批量执行。
- 异步批次创建请求只进行授权、范围校验、签到范围快照持久化和任务入队，提交成功后立即返回批次标识，不在该 HTTP 请求中访问外部站点。
- 批次创建接受客户端幂等标识；网络重试或 Cloudflare 响应丢失后重复提交同一标识，必须返回原批次而不是创建新批次。
- 服务端负责后台串行执行、更新批次进度和持久化结果；工作台只对执行中的批次进行周期性轮询，并提供手动刷新。批次状态响应必须返回 `Cache-Control: no-store`，避免代理缓存过期进度。
- 前端为批次创建、状态查询和工作台聚合查询设置有限的控制请求超时；控制请求失败时允许重新查询，绝不自动重新创建批次。
- 页面离开或刷新不停止批次。第一阶段不提供服务端中途取消或暂停操作；批次启动后继续执行，仅对停滞批次提供经过权限校验的手动重新入队入口。
- Cloudflare 或浏览器连接中断时，服务端批次继续执行；前端恢复连接后凭批次标识继续轮询。
- 单账号外部请求继续使用有限超时；单个账号超时记录为可重试失败，批次继续执行后续账号，不因单个站点拖住整个批次。
- 确认操作锁定签到范围快照。筛选条件在批次执行期间发生变化，不影响已创建批次；详情必须能展示实际账号范围及跳过原因。
- 服务端是跳过规则和每日尝试上限的最终判断来源。已成功、停用、关闭重试、达到每日上限或其他不符合条件的账号不能被前端绕过规则强行执行。
- 同一签到账号不能同时出现在多个执行中的签到批次中。发生冲突时，工作台展示已占用的批次及其进度。
- 每个实际执行的账号生成独立签到记录；重试生成新记录，不覆盖历史记录。仅被跳过的账号不伪造一次实际执行记录，但必须出现在签到范围和批次汇总中。
- `already_checked` 在界面显示为“今日已签到”，在批次汇总中属于已完成，但不计作本次新成功。
- 首屏指标按当前用户可见范围和业务日期由后端完整计算，不受当前分页或已加载数量影响。点击指标可复用对应筛选条件。
- 工作台数据使用聚合读取能力一次获得首屏所需的完整指标、可执行账号、执行中/最近批次、余额预警和最近失败；现有账号、记录、统计等接口继续服务原页面。
- 工作台作为默认页面新增到现有导航中；账号管理和签到记录继续保留为独立页面，工作台只负责今日运营编排和快速处理。
- 工作台推荐布局为：页头与业务日期/刷新操作、四项核心指标、待处理账号主区域、执行中和最近批次侧区域、余额预警与最近失败区域。移动端改为单列流式布局和固定批量操作入口。
- 账号表格支持服务端分页或加载更多并显示总数量。行级操作提供单账号签到、刷新余额、编辑和查看记录；启用、停用、删除等影响性操作需要确认。
- 批次详情使用侧边抽屉或可展开区域，保留工作台上下文，支持逐账号结果、失败原因和跳转到签到记录筛选结果。
- 账号状态和余额预警使用两个独立维度；状态颜色只表达状态语义，不把余额风险伪装成签到状态。
- “今日”统一按平台业务时区判断，默认 `Asia/Shanghai`。工作台显示业务日期和时区，签到跳过、统计和每日尝试上限使用同一口径。
- UI 继续使用 Vue 3、TypeScript、Naive UI 和现有明暗主题能力，不迁移框架或组件库。视觉升级采用统一的字体层级、数据数字等宽/等宽数字、克制的单一强调色、清晰的表格层级和响应式间距。
- 交互提供骨架屏、空状态、错误状态、可复制反馈、键盘焦点和 180–240ms 的克制过渡，并遵循 `prefers-reduced-motion`。不使用依赖大量装饰动画的操作反馈。
- 批次汇总和关联签到记录遵循同一清理策略，避免只保留汇总或只保留明细造成历史口径分裂。
- 已接受的“持久化签到批次”架构决策记录在对应 ADR 中。

## Testing Decisions

- 测试只验证用户可观察的业务行为和状态转换，不绑定私有函数、组件内部变量或数据库实现细节。
- 后端以“签到批次生命周期”作为最高测试边界：使用测试数据库和可控的站点执行替身，验证批次创建、签到范围快照、后台状态变化、轮询结果、批次汇总、逐账号记录、跳过规则、每日上限、重复执行保护、权限隔离和历史保留。
- 后端至少覆盖兼容同步模式和工作台异步模式，确认旧调用方行为不变，异步调用能在执行完成前取得批次标识并读取进度。
- 后端测试补充页面刷新/重复查询语义、站点不可用的可重试失败、脱敏错误信息和同一账号跨批次冲突。
- 后端测试使用延迟站点执行替身，确认异步创建在外部签到尚未完成时已经返回批次标识，并且轮询能读取持续变化的进度。
- 后端测试确认重复幂等创建只得到同一个批次、状态查询声明禁止缓存、单账号超时不终止后续账号，且同步兼容模式的既有行为不变。
- 前端以“签到工作台交互”作为最高测试边界：用模拟 API 响应验证指标、筛选、账号选择、确认预览、批次轮询、刷新后恢复、结果详情、单条/批量重试和权限数据范围。
- 前端优先复用现有 `node:test`，将工作台的筛选、选择、状态归类、批次汇总和轮询状态转换提取为可测试的交互模型；不为测试目的引入不必要的框架。
- 前端交互测试覆盖首次使用、无账号、无匹配结果、加载中、网络错误、权限不足、执行中、部分失败、全部失败和移动端操作入口等状态。
- 通过前端生产构建、后端测试和人工浏览器验收确认视觉层级、响应式布局、键盘焦点、暗色主题、脱敏错误和 `prefers-reduced-motion` 行为。
- 真实外部站点不参与自动化测试；站点适配器的现有解析测试继续独立运行。

## Out of Scope

- 不在第一阶段扩展自动调度的业务能力，不重新设计 cron 策略或调度执行规则。
- 不在第一阶段扩展通知渠道、通知节流规则或统计分析指标体系；只提供工作台所需的现有状态读取和入口。
- 不在第一阶段重做用户管理、角色体系或普通用户的个人设置。
- 不在第一阶段增加服务端批次取消、暂停或无限自动重试；停滞批次的有限手动重新入队属于故障恢复入口。
- 不引入 WebSocket、SSE 或新的前端框架；工作台使用现有技术栈和轮询模型。
- 不在第一阶段实现源站服务重启后的批次自动续跑；服务重启恢复另立后续票据，当前应提供可识别的需要恢复状态和安全重试入口。
- 不修改外部站点适配器的业务规则，不以本功能为由变更凭据加密、Cookie、CSRF 或权限安全模型。
- 不进行全站营销页式重设计；视觉工作聚焦签到工作台、其导航入口和直接相关的账号/记录交互。
- 不在本规格中解决 CSV 跨用户归属、普通用户修改密码、通知结果持久化等独立问题，除非实现工作台时发现它们是不可绕过的阻塞项。

## Further Notes

- 当前代码已经有批量签到后端能力，但前端主要循环调用单账号接口；这是第一条实现主线，完成后“批量手动”筛选、每日上限和批次汇总才会拥有统一口径。
- Cloudflare 代理域名是硬部署约束：浏览器请求只负责短生命周期的控制操作，不能依赖 Cloudflare 的长请求超时阈值来承载整批签到。
- 当前前端已有页面内批量进度和停止入口。迁移到服务端持久化批次后，停止入口应改为执行中说明和后台运行提示，不再把页面卸载当作停止批次。
- 工作台的批次详情应能链接到签到记录页面的筛选结果，但不应让管理员失去当前工作台筛选和批次上下文。
- 规格完成后应拆分为依赖顺序明确的垂直票据，每张票据都应能独立演示或验证一条跨后端、前端和测试的完整路径。
